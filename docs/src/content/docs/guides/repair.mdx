title: Health Checker & Repair
description: Per-entry health tracking with scheduled sweeps and on-demand rechecks.
---

The health checker tracks the state of every entry in your library and runs scheduled sweeps that re-probe only the entries that actually need checking. Each entry carries a health status visible in Browse, and you can force a recheck of a single entry at any time — independent of the global schedule.

## Concepts

### Entry health

Every entry has exactly one health record with one of these statuses:

| Status        | Meaning                                                        |
|---------------|----------------------------------------------------------------|
| `healthy`     | All probed files are reachable.                                |
| `broken`      | At least one file failed its probe.                            |
| `repairing`   | A sweep is currently probing or fixing this entry.             |
| `unknown`     | Probe was inconclusive (no files broken, none confirmed OK).   |
| `stale`       | Last check is older than `recheck_interval`.                   |
| `unsupported` | The entry has no probe path on this protocol.                  |

Each record also stores the file fingerprint, last-checked / last-OK / last-failed timestamps, the next-due time, and the list of broken files (with their Arr IDs when the source is Arr).

When an entry's file set changes, its fingerprint is invalidated and the entry is marked **dirty**, forcing a re-probe on the next sweep.

### Sweeps

A **sweep** is a single pass that selects candidate entries, probes them, and applies whichever of the `repair` / `prune` / `regrab` components are enabled to the broken ones. Sweeps are recorded as **runs** (history-only — you cannot create a run by hand).

A sweep does not scan your whole library every time. It selects only entries where:

- status is not `healthy`, **or**
- the entry is dirty, **or**
- the entry has never been checked, **or**
- the entry's `next_check_due_at` has passed.

Healthy entries that haven't changed since the last successful check are skipped.

### Single-entry recheck

You can force a recheck on any one entry from the Browse UI or the API. This works even when the global health checker is disabled and does not produce a run record. Repairs should be triggered through the Arr integration.

## Configuration

```json
{
  "repair": {
    "enabled": true,
    "source": "arr",
    "schedule": "0 4 * * *",
    "workers": 5,
    "strategy": "per_entry",
    "recheck_interval": "168h",
    "arrs": [],
    "repair": true,
    "prune": false,
    "regrab": false,
    "max_deletions_per_run": 100,
    "skip_nzb_repair": false,
    "notify_on_complete": false,
    "nntp_connection_percent": 20,
    "stop_schedule": "06:00"
  }
}
```

| Field                     | Description                                                                              | Default     |
|---------------------------|------------------------------------------------------------------------------------------|-------------|
| `enabled`                 | Master switch. When off, no scheduled sweep runs (single rechecks still work).           | `false`     |
| `source`                  | Where to enumerate from: `arr` (walk Arr media) or `managed` (walk managed entries).     | `arr`       |
| `schedule`                | Cron expression for the recurring sweep. Required when `enabled` is `true`.              | —           |
| `workers`                 | Number of concurrent probe workers.                                                      | `5`         |
| `strategy`                | `per_entry` (stop after first broken file in an entry) or `per_file` (probe all files).  | `per_entry` |
| `recheck_interval`        | How long a healthy entry's check stays fresh before it becomes a candidate again.        | `168h`      |
| `arrs`                    | Optional filter when `source=arr`. Empty list means all eligible Arrs.                   | `[]`        |
| `auto_repair`             | **DEPRECATED and ignored.** Kept only so older configs still load. See the caution below. | — |
| `repair`                  | REPAIR component: re-acquire a dead item from the providers. Non-destructive.            | `true` (when unset) |
| `arr_delete`              | ARR-DELETE component: delete the Arr's file record, and nothing else by itself. Destructive. Formerly `regrab`, still accepted as an alias. | `false` |
| `arr_search`              | Sub-action of `arr_delete`: ask the Arr for a replacement after the delete. Does nothing on its own. | `false` |
| `arr_blocklist`           | Sub-action of `arr_delete`: ban the release globally and permanently. Does nothing on its own. | `false` |
| `prune`                   | PRUNE component: delete the item decypharr-side only (never calls the Arr). Destructive. | `false`     |
| `max_deletions_per_run`   | Caps how many entries one run may destructively act on. `0`/unset → `100`; negative → unlimited. | `100` |
| `max_live_prunes_per_hour`| Explicit absolute ceiling on the PRUNEs that happen on a **read** instead of inside a run — a confirmed debrid takedown, a confirmed usenet dead article. Overrides `live_prune_percent` when set. `0`/unset derives the bound proportionally (below); negative → unlimited. | derived |
| `live_prune_percent`      | The proportional bound: what share of the library may be live-pruned per rolling hour, as `max(250, percent × entries)`. Sized so a genuine takedown wave of hundreds passes untouched while a mass-deletion runaway trips it. Over budget the entry is still condemned and still stops serving; only the deletion is deferred to the next sweep. `0`/unset → `10`; negative → floor only. | `10` |
| `skip_nzb_repair`         | Skip NZB / Usenet entries during scheduled sweeps.                                      | `false` |
| `notify_on_complete`      | Send a notification when a sweep finishes.                                               | `false`     |
| `nntp_connection_percent` | Percentage of NNTP connections the probe is allowed to use. Avoids starving downloads.   | `20`        |
| `stop_schedule`           | Optional cron expression, clock time, or interval. If a repair sweep is still running when this fires, it's stopped early. Leave empty to always run to completion. | — |

:::caution[`auto_repair` no longer controls anything]
What a sweep *does* to a dead item is decided by three independent component knobs, in the order
a sweep runs them — `repair` (re-acquire), `arr_delete` (delete the Arr's file record) and `prune`
(delete decypharr-side only) — not by `auto_repair`, which the resolver ignores entirely. A sweep
is detect-only (CHECK-only) exactly when all three are off; setting `auto_repair: false` does
**not** make it detect-only. Nothing is deleted until you opt into `arr_delete` and/or `prune`.
Full behavior, including how the manual endpoints select components, is in the
[API reference](/reference/api).
:::

:::caution[REPAIR cannot fix nzb entries — only torrents]
`repair` (re-acquire) applies to **torrent entries only**. Re-acquisition for usenet is not
sound: re-parsing the staged NZB asks the same providers for the same message-ids, so it cannot
resurrect a missing or payload-less article. A dead nzb entry is actionable only via `arr_delete`
(delete the Arr's file record, optionally with `arr_search` to ask for a replacement) or `prune`
(delete decypharr-side — which recovers nothing, it only stops decypharr serving a dead entry).

So a REPAIR-only configuration on an nzb-heavy library fixes **nothing** — and until now it did
so silently. Every entry REPAIR declines for this reason is counted as
`repair_skipped_unsupported` in the run stats (shown on the repair page as **Repair n/a**, and
per entry in the expanded broken-entry row). If that number is high, turn on `arr_delete` and/or
`prune` — or set `skip_nzb_repair` to stop sweeping nzb entries at all.
:::

### Stop schedule

`stop_schedule` is useful when a repair sweep needs to finish (or get out of the way) before something else happens — for example, before your overnight maintenance window ends, or before peak-usage hours when probes would compete for bandwidth.

- The repair sweep is cancelled at the next firing of `stop_schedule`, mid-probe if necessary. Entries not yet probed are left as they were before this repair sweep (their existing health and `next_check_due_at` are untouched, so they're picked up again on the next scheduled run).
- The run is recorded as `completed` (not `cancelled`), with `cancel_reason` noting it was stopped by schedule.
- What happens to entries this repair sweep *did* manage to probe and found broken is controlled by the enabled components, same as any other repair sweep:
  - any of `repair` / `prune` / `regrab` on → those components are applied to what was found broken.
  - all three off → the entries are just recorded as broken; nothing is re-acquired or deleted.

#### Multi-day coverage

Each repair sweep probes due entries **oldest-checked-first** (never-checked entries first, then least-recently-checked, ...). Probing an entry updates its `last_checked_at` immediately, which moves it to the back of the queue for future repair sweeps.

This means a repair sweep scheduled daily with a `stop_schedule` (e.g. `schedule: "0 0 * * *"`, `stop_schedule: "0 9 * * *"`) makes guaranteed forward progress across days, as long as `recheck_interval` is comfortably longer than the time it takes to cycle through the whole library:

- Day 1, 00:00–09:00: probes the oldest N due entries (or however many fit in 9 hours), marking each one's `last_checked_at` as it finishes.
- Day 1, 09:00: `stop_schedule` fires, the repair sweep stops. The remaining entries are untouched and stay oldest in the queue.
- Day 2, 00:00: the next repair sweep's `due` set excludes everything probed on day 1 (their `last_checked_at` is now within `recheck_interval`), so it continues with the next-oldest N.
- This repeats until the whole library has been probed within one `recheck_interval` window, then the cycle restarts from the oldest again.

If a full repair sweep would take 2 days at 9 hours/day but `recheck_interval` is `168h` (1 week), this comfortably completes a full pass well before entries become due again. If `recheck_interval` is shorter than the time a full cycle actually takes, some entries may go stale before they're re-probed — increase `recheck_interval`, the daily window, or `workers` to compensate.



### Strategies

- **`per_entry`** — probe stops at the first broken file in an entry. Faster on broken libraries; sufficient when you only need to know "is this entry intact?".
- **`per_file`** — probe every file. Use when you want a complete broken-file list per entry (e.g. to drive a per-file Arr re-acquire).

### Sources

- **`arr`** — walks Sonarr / Radarr media, resolves each item to an entry through the symlink target, and probes that entry. Broken files are enriched with Arr identifiers so repair can call `DeleteFiles` + `SearchMissing` directly.
- **`managed`** — walks managed entries directly. Used when you don't have an Arr in front, or for entries imported outside the Arr flow. NZB-only managed brokens have no Arr re-acquire path; they stay `broken` with `failure_reason=usenet_segment_missing` for you to react to manually.

## Workflow

1. The cron tick (or a manual **Run Now**) opens a new run.
2. Candidates are selected per the rules above.
3. For each candidate, the entry is marked `repairing` and probed by a worker.
4. The entry's health is updated with the probe outcome (`healthy` / `broken` / `unknown`), broken files, fingerprint, and timestamps.
5. If `arr_delete` is on and the entry has Arr-known broken files, they are batched per Arr and their file records deleted — plus a blocklist and/or search only where `arr_blocklist` / `arr_search` are enabled. If `prune` is also on, it runs after that. After the repair attempt, only those entries are re-probed.
6. The run record's stats are updated live throughout, so the status panel reflects progress without needing to wait for completion.

A failure to persist a single entry's health update is logged but never aborts the sweep.

## Stop and disable

- **Stop** cancels the active run. In-flight probes return at the next checkpoint, the run is marked `cancelled`, and entries that hadn't yet finished probing revert to their previous status.
- **Disable** (`enabled=false`) cancels any in-flight run and unregisters the cron job. Per-entry health data is **kept**, so Browse badges stay meaningful and single-entry rechecks remain available.

## Singleton invariants

- At most one sweep runs at a time. Triggering a second one returns `409 Conflict`.
- A force-recheck on an entry that is already being probed by the active sweep returns `409 Conflict`.

## API

| Method   | Path                                  | Purpose                                                                  |
|----------|---------------------------------------|--------------------------------------------------------------------------|
| `GET`    | `/api/repair/config`                  | Read current config.                                                     |
| `PATCH`  | `/api/repair/config`                  | Partial update. Omitted keys keep their current values.                  |
| `PUT`    | `/api/repair/config`                  | Full replacement. **Omitted keys are cleared** — `max_deletions_per_run`, `stop_schedule`, `prune` and `regrab` included. |
| `GET`    | `/api/repair/status`                  | Active run summary, last completed run, and counts of entries by status. |
| `POST`   | `/api/repair/run`                     | Trigger a sweep now. Body can include `ignore_last_checked`, `repair`, `prune`, `regrab`, `unrestrict_link`, and `protocol`. |
| `POST`   | `/api/repair/stop`                    | Cancel the active run.                                                   |
| `GET`    | `/api/repair/runs`                    | Run history.                                                             |
| `GET`    | `/api/repair/runs/{id}`               | Run detail.                                                              |
| `DELETE` | `/api/repair/runs`                    | Clear run history.                                                       |
| `GET`    | `/api/repair/health`                  | List entry health (optional `?status=broken`).                           |
| `GET`    | `/api/repair/health/{name}`           | Per-entry health, including the broken-file list.                        |
| `POST`   | `/api/repair/health/{name}/check`     | Force-recheck this entry.                                                |
| `POST`   | `/api/repair/recheck/media`           | Recheck a single Arr media item. Body: `{arr, media_id, fix}`. Repairs run through Arr. |

### Examples

Change one setting without disturbing the rest — use `PATCH`:

```bash
curl -X PATCH http://localhost:8282/api/repair/config \
  -H "Authorization: Bearer YOUR_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"max_deletions_per_run":25}'
```

The same body sent with `PUT` would *also* clear `stop_schedule`, `prune`, `regrab`, `arrs` and the
`repair` tri-state, and turn the sweep off — `PUT` replaces the whole block with what you sent.
Reach for it only when you are submitting a complete repair config.

Run a sweep now:

```bash
curl -X POST http://localhost:8282/api/repair/run \
  -H "Authorization: Bearer YOUR_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"protocol":"all","unrestrict_link":true}'
```

Stop the active sweep:

```bash
curl -X POST http://localhost:8282/api/repair/stop \
  -H "Authorization: Bearer YOUR_API_TOKEN"
```

Force-recheck a single entry:

```bash
curl -X POST 'http://localhost:8282/api/repair/health/My.Show.S01/check' \
  -H "Authorization: Bearer YOUR_API_TOKEN"
```

Recheck a single Sonarr series and repair it if broken:

```bash
curl -X POST http://localhost:8282/api/repair/recheck/media \
  -H "Authorization: Bearer YOUR_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"arr":"Sonarr","media_id":"123","fix":true}'
```

## Browse page

Each entry row carries a health badge whose colour reflects the current status (healthy / broken / repairing / unknown / stale / unsupported). Hovering shows the last-checked time, broken-file count, and top failure reason. The row's action menu has **Recheck health**, and clicking the badge opens a side panel listing every broken file with its reason and Arr link.

The badges flip live during a sweep — entries move through `repairing → healthy/broken` as the workers report results, without needing to refresh after the run finishes.

## Per-Arr and per-protocol skips

Disable repair for specific Arrs:

```json
{
  "arrs": [
    { "name": "Sonarr", "skip_repair": true }
  ]
}
```

Skip repair for all NZB / Usenet entries:

```json
{
  "repair": {
    "skip_nzb_repair": true
  }
}
```

## Rate limiting

Probes against debrid providers respect a separate rate limit so they don't starve regular downloads:

```json
{
  "debrids": [
    { "provider": "realdebrid", "repair_rate_limit": "60/minute" }
  ]
}
```

For Usenet probing, `nntp_connection_percent` (above) caps the share of NNTP connections the health checker uses.

:::caution
With `arr_delete: true` (formerly `regrab`), a sweep deletes the broken Arr file
records — and **only** that. Blocklisting and searching are separate opt-ins
(`arr_blocklist`, `arr_search`), both default-off and both subordinate to
`arr_delete`. If you enable `arr_search`, verification of the resulting
re-acquires happens later: the Arr import is asynchronous and the badge flips to
`healthy` once the replacement file is in place.

With `prune: true` the item is deleted **decypharr-side only and no Arr call is
made at all**. Do not expect the Arr to notice: the Arr's file record still
points at a symlink that is now dangling, and its cleanup scan compares paths
without stat-ing them, so the record is kept and nothing is re-searched. PRUNE is
the action that leaves the Arr alone — that is the point of it, not a caveat.
:::

## Troubleshooting

### Sweep takes too long

Increase `workers`, or raise `recheck_interval` so fewer entries become candidates each tick:

```json
{
  "repair": {
    "workers": 10,
    "recheck_interval": "336h"
  }
}
```

### Sweep is too aggressive

Lower `workers`, lengthen `schedule`, lower `max_deletions_per_run`, or turn all three of `repair` / `prune` / `regrab` off to run detect-only and review brokens before acting on them.

### One entry keeps flipping broken

Open its detail panel from Browse to see the broken-file list and reason. For Arr-sourced entries, trigger fixes through the Arr integration without waiting for the next sweep.

## Migration from v1

The job-based repair system (`repair_jobs`, `repair_keys`, the **Add Job** UI) has been removed. On first boot of the new system the legacy buckets are dropped, and existing recurring schedules do **not** carry over — re-enable repair once with the new config.

Per-entry health records (`repair_state`) are forward-compatible; new fields default to empty and populate on the next probe.
